# multi-model-routing — 투 메인 멀티모델 라우팅 원칙

**핵심: 최고 모델은 판단에, 실행은 그 일에 가장 싼 정확한 모델에.**

## 투 메인 체제
- **판단 메인**: 지휘·게이트·설계 검증·릴리스 판단 — 벤치마크상 심층 판단·레포 정합성이 강한 쪽(2026-07 기준 Claude 최상위: SWE-Bench Pro·GDPval 계열 우위).
- **실행 메인**: 대규모 구현·에이전틱 코딩 라운드 — 하네스 실행 효율(속도·토큰·비용)이 강한 쪽(2026-07 기준 GPT-5.6 Sol: 에이전틱 코딩 지수 우위+비용 1/3).
- 나머지 모델은 역할 특화: 대용량 리뷰·탐색 스캔(밸런스 티어), 빠른 반복(최저가 티어 low effort), 설계 스펙(판단 계열 상위), 중형 구현·분석 팬아웃(판단 계열 중위), 잔손질(최소 모델).

## 라우팅을 정하는 방법 (모델명이 아니라 절차)
1. **공식 포지셔닝 문서**를 먼저 — "start here for demanding agents" 같은 벤더의 자기 선언이 1차 지도.
2. **벤더 벤치마크는 벤더 발표로 취급** — 자사 우위 수치와 자인 열위 수치를 함께 수집(자인 열위가 더 신뢰됨).
3. **로컬 프로브로 검증** — 동일한 미묘한 과제(예: 3버그 헌트+비버그 감별)를 후보 전 모델에 주고 시간·토큰·정확도 3축 실측. 벤더 주장과 다르면 실측 우선.
4. **effort/모드 계층 파악** — 같은 모델도 effort로 완전히 다른 프로파일("헤비 리즈너"처럼 보이는 게 기본값 아티팩트일 수 있음). 상한 초과 지정은 400 — 모델별 상한 매핑.
5. 매트릭스를 스킬로 고정하고, 신모델·벤치 갱신 시 프로브 재실행.

## 교차 검증 규칙
같은 회사 모델끼리 자기 검증 금지 — A사 모델이 만든 것은 B사 모델이 검토. 최종 게이트는 판단 메인이.

## 운영 함정 (실증)
- CLI 구버전이면 신모델 400("requires a newer version") — 하네스 장애의 흔한 원인. 업그레이드 먼저.
- 협업 네이티브 모델(예약 도구 스키마)은 기존 config 키와 충돌 가능 — 전용 홈/프로필 분리(인증은 심링크로 신선도 유지).
- 멀티에이전트 모드(예: ultra=4병렬)는 토큰 배수 — 명시 지정 시만.
